# LLM Gateway

夹在应用和模型供应商之间的一层。在此之前 `llm.py` 是 43 行裸 SDK 调用：
单一供应商、无重试、无计费、无限流、无缓存。

## 做什么

| 能力 | 解决的问题 |
|---|---|
| 多 provider 抽象 | 换供应商只改配置，不改代码 |
| 故障转移 | 主供应商挂了自动切备用，不是整站不可用 |
| 重试 + 指数退避 | 网络抖动不该直接失败 |
| 用量计费 | 回答「每天多少 token、花多少钱」 |
| 限流 | 单个调用方刷不爆整个配额 |
| 缓存 | 相同问题不重复付费 |

## 结构

```
providers.py   Provider 数据类 + 从环境变量装配注册表
policies.py    错误分类、退避、令牌桶限流、LRU+TTL 缓存、计量器
core.py        Gateway 主体：编排上面几件事
```

`llm.py` 现在是 Gateway 的薄封装，**上层调用方一行未改**。

## 三个关键设计

### 1. 错误分类：不是所有错误都该重试

无差别重试是 Gateway 最容易犯的错。401（key 错）、400（参数错）重试多少次
都是同样结果，只会拖慢用户、放大账单。429/5xx/超时才是瞬时故障。

429 尤其要小心：供应商已经在喊「你太快了」，此时无脑重试等于火上浇油。
所以 429 要重试，但退避基数翻倍。

退避带随机抖动。没有抖动的话，并发失败的请求会按固定间隔同时再次撞上供应商，
形成「重试风暴」，反而更难恢复。

### 2. 流式下故障转移只在首个分片之前有效

一旦有内容发给了客户端，就不能再换 provider 重来——用户已经看到半句话，
换个模型重新生成会导致回答从中间断裂、前后矛盾。

所以 `chat_stream` 把「建流」和「消费流」分开：建流阶段允许失败转移，
进入消费阶段后任何异常直接抛给上层。

流式也不走缓存：要缓存就得先收完整个流再回放，那就失去了「首字快」的意义。

### 3. 只做精确匹配缓存，不做语义缓存

语义缓存（把问题向量化、找相似的旧问题直接返回）要为每次请求多付一次
embedding 和一次向量检索，而且「多相似算同一个问题」是个很难调的阈值——
调松了会张冠李戴，把上一个用户的答案返回给你。在客服场景里这是事故。

精确匹配命中率低，但绝不会答错。

## 用量统计

```bash
curl -s http://127.0.0.1:8000/gateway/stats -H 'X-API-Password: <密码>'
```

返回调用次数、token 分布、估算成本、缓存命中率、各 provider 分布。
加了鉴权——用量数据能反推业务量，不该公开。

⚠️ **单价默认是 0**，因为编一个价格比留空更糟。真实单价请查各家控制台后
填进环境变量 `DASHSCOPE_PRICE_IN` / `DASHSCOPE_PRICE_OUT`（每百万 token）。

## 配置

```bash
LLM_MAX_ATTEMPTS=3        # 每个 provider 内部重试次数
LLM_RATE_PER_MIN=0        # 每个调用方每分钟上限，0 = 不限流
LLM_CACHE_TTL=600         # 缓存存活秒数

DEEPSEEK_API_KEY=...      # 配了才启用故障转移，没配也不报错
```

注意总尝试次数是 `LLM_MAX_ATTEMPTS × provider 数量`，别把两者都调大。

## 已知边界

- **计量只在内存里**，进程重启即清空。生产应写进时序库或日志系统
- **限流是单进程的**。多副本部署时每个副本各算各的，实际配额是配置值 × 副本数。
  要精确控制得用 Redis 之类的共享计数器
- **embedding 未接入 Gateway**。`rag/store.py` 仍走 langchain 的 `OpenAIEmbeddings`，
  因为换掉会牵连已建好的索引。Gateway 的 `embed()` 已实现但暂未被使用
